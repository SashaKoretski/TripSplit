# AI_REVIEW

## WebLab#2 - проектирование REST API и OpenAPI (2026-10-07)

**Задача**: спроектировать и проверить OpenAPI 3.1 контракт публичного REST
API для TripSplit по `ai/tasks_web/LAB02.md`. Контракт не копирует существующий
API, потому что его не было: `TripSplit.WebUI` - чистый server-rendered
ASP.NET Core MVC (Razor views, cookie-сессия, без AJAX/fetch, без
`[ApiController]`), подтверждено чтением всех контроллеров и `Program.cs`.

**Агент/модель**: Claude (Sonnet 5), Claude Code CLI.

**Ключевые созданные/измененные артефакты**:

- `src/openapi/openapi.yaml` - контракт OpenAPI 3.1.0: `/api/v1`, 14 путей,
  24 уникальных `operationId`, 20 схем. Полный CRUD + обязательный `PATCH`
  (JSON Merge Patch) - сущность `Expense`.
- `src/openapi/redocly.yaml`, `src/openapi/package.json`,
  `src/openapi/.gitignore` - конфиг и закрепленные версии инструментов
  проверки (`@redocly/cli@2.60.0`, `@stoplight/prism-cli@5.14.2`).
- `docs/api/README.md` - обзор контракта, версия, авторизация, карта
  ресурсов, обоснование CRUD/PATCH сущности.
- `docs/api/scenario-mapping.md` - SC-001..003 (WebLab#1) разложены по шагам
  с `operationId`/методом/путем/ожидаемым результатом.
- `docs/api/review.md` - семантическое ревью (Этап 5 LAB02): коды ошибок
  1:1 с доменными исключениями, спорные места (BR-08 при регистрации,
  идемпотентность участников, асимметрия `DELETE` чека и статуса поездки,
  `404` вместо anti-enumeration `401` в `/auth/token`), результаты lint и
  mock-проверки.

Файлы документации - не в `docs/weblab02/`, а по смыслу (`docs/api/`) - по
уже принятому в WebLab#1 правилу не делить документацию по номерам лаб
(зафиксировано отдельно в памяти ассистента, не только здесь).

**Выполненные проверки**:

- Полное чтение `TripSplit.WebUI` (все контроллеры, `Program.cs`, сессия),
  `TripSplit.BusinessLogic` (все модели, интерфейсы и реализации сервисов),
  `init.sql` - для точного соответствия контракта бизнес-правилам BR-01..11
  и реальным доменным исключениям.
- `src/openapi/openapi.yaml` проверен `PyYAML` (синтаксис, уникальность
  `operationId`) и `redocly lint` (0 ошибок, 0 предупреждений после
  исправления 3 реальных ошибок 3.1-совместимости `nullable` и 9+
  предупреждений по нереалистичным примерам id - подробности в
  `docs/api/review.md`).
- `prism mock` - сервер поднят, все 24 маршрута разрешены без ошибок;
  прогнан многошаговый сценарий SC-002/SC-003 (создание поездки -> чек ->
  трата -> `PATCH` привязки/отвязки чека -> расчет -> удаление -> завершение
  поездки) через `curl`, все статусы совпали с контрактом, включая негативный
  кейс (`400` при отсутствии обязательных полей).

**Ключевые решения, принятые пользователем**:

1. Версия API - `/api/v1` (публичного API раньше не было).
2. Аутентификация - `POST /auth/token {email}` -> JWT без refresh (в
   развитие ADR-001 из WebLab#1, которое уже разделило auth Web UI/API).
3. `POST /users` возвращает только `User`, без токена.
4. Участники поездки - единый ресурс `POST /trips/{id}/participants`
   (self-join пустым телом, invite-by-email телом `{email}`), без отдельной
   сущности "приглашение".
5. Завершение поездки - `POST /trips/{id}/finish` (RPC для необратимого
   перехода), не `PATCH` статуса.
6. Привязка трат к чеку - через `PATCH /expenses/{id} {"receiptId": ...}`,
   без отдельного bulk-эндпоинта (заменяет RPC `AttachExpenses`).
7. Полный CRUD и `PATCH` - сущность `Expense`; семантика `PATCH` - JSON
   Merge Patch (RFC 7396).
8. `DELETE` - soft delete для Trip/Expense, hard delete для Receipt/Image
   (как в схеме БД); повторный `DELETE` -> `404`.
9. Пагинация - только `GET /trips` и `GET /trips/{tripId}/expenses`.
10. `GET /receipts/{id}/image` -> `302` редирект на presigned S3 URL.
11. `403` для не-участника поездки - целевое поведение контракта, не
    совпадает с текущим пробелом в Web UI (`TripsController.Details`).
12. Инструмент проверки - Redocly CLI (lint) + Prism (mock), версии
    зафиксированы в `package.json`.
13. Этап 5 (пять спорных мест семантического ревью в `docs/api/review.md`)
    подтвержден как есть, без изменений.
14. Этап 7 (управляемое изменение) - `PUT /receipts/{id}/image`: добавлены
    явный лимит 10 МБ (`maxLength`), `enum` допустимых content-type через
    `encoding`, и новый статус `413 file_too_large`, отдельно от `422`.
    После изменения повторены `lint` (0/0) и `prism mock` (все 24 маршрута
    резолвятся), обновлена `scenario-mapping.md`.

**Отклоненные альтернативы**:

- `/api/v2` "на будущее" - отклонено: до этой лабы публичного API не было,
  версионировать было бы нечего, `v2` ввел бы в заблуждение.
- Отдельная сущность `invitation` с состоянием подтверждения для приглашения
  участников - отклонено: добавление потребовало бы новой бизнес-логики
  (`TripService.AddParticipantAsync` добавляет участника немедленно, без
  подтверждения), что запрещено в этой лабе.
- JSON Patch (RFC 6902) вместо JSON Merge Patch для `PATCH /expenses/{id}` -
  отклонено как избыточное: точечные list-операции не нужны ни одному
  сценарию WebLab#1.
- Anti-enumeration `401` вместо `404` в `POST /auth/token` при
  незарегistrированном email - отклонено: email и так раскрывается через
  `POST /trips/{id}/participants` (приглашение), система не использует
  пароли/секреты, которые имело бы смысл защищать этим способом.
- Spectral вместо Redocly CLI для lint - не выбран пользователем
  (предложен как альтернатива, выбрана рекомендация Redocly CLI + Prism).

**Зафиксированные, но не исправленные пробелы** (контракт описывает их явно,
бизнес-логика не менялась):

- `ReceiptService.DeleteAsync` не проверяет статус поездки, в отличие от
  `CreateAsync` - асимметрия описана в `docs/api/review.md`, решение о том,
  устранять ли ее, - для WebLab#3.
- Проверка членства в поездке (`403` для не-участника) - целевое поведение
  контракта, в MVC (`TripsController.Details`) сейчас не реализовано (пробел
  уже зафиксирован в WebLab#1).

**Реорганизация структуры (2026-10-08, по запросу пользователя)**:
`openapi/` перемещен в `src/openapi/` (контракт и инструменты проверки -
рядом с остальным кодом, не в корне репозитория); `img/` слит в `docs/`
(пользователь хотел единое место для всей документации и диаграмм, `docs/`
уже существовал с WebLab#1). Обновлены все ссылки: `README.md`,
`docs/details.md` (пути к изображениям), `docs/api/README.md`,
`docs/api/review.md` (пути к контракту) и записи этого файла. Содержимое
файлов не менялось, только путь.

## WebLab#1 - анализ, требования и архитектура (2026-09-24)

**Задача**: восстановить и оформить фактическую архитектуру, требования и
пользовательские сценарии существующей системы TripSplit (Web UI) по
`ai/tasks_web/LAB01.md`, закрыть пробелы согласно условию.

**Агент/модель**: Claude (Sonnet 5), Claude Code CLI.

**Ключевые созданные/измененные артефакты**:

- `README.md` - переписан: цель проекта, FR/NFR, use-case, BPMN, 3 сценария, ER,
  технологический стек, диаграмма БД, C4 (Context/Container/Component), черновые
  эскизы экранов, 2+ ADR - весь обязательный минимум изложен прямо в тексте,
  без ссылок на другие файлы
- `docs/details.md` (новый) - развернутая версия того же материала (полные FR/BR,
  полные сценарии, трассировка, карта экранов, полные ADR) плюс то, что не входит
  в обязательный минимум (sequence-диаграммы, C4 L4, конкуренты, инструкция сборки)
- `docs/Business-process/bpmn-create-trip.puml`, `bpmn-add-expense.puml`, `bpmn-settlement.puml` (новые; PNG сгенерированы пользователем)
- `docs/Use-case/Use-Case.puml` - формулировка входа поправлена под факт (email вместо Google)
- `docs/DBML/DBML.dbml` - аннотация `google_id` поправлена под факт
- `docs/ER/ER.puml` - `Transfer`/`TripStatistics` помечены как производные (не хранятся в БД)
- `docs/Business-process/b_process.drawio` - оставлен как обзорная сквозная схема, детализация вынесена в три новых BPMN рядом

Пути выше даны по состоянию на 2026-10-08: изначально (WebLab#1, 2026-09-24)
эти файлы создавались в отдельной папке `img/`, которую пользователь позже
попросил слить в `docs/` - все ссылки в этой записи обновлены на новое
место, факт создания и содержание файлов не изменились.

Промежуточный вариант (`docs/requirements.md`, `scenarios.md`, `traceability.md`,
`screens.md`, `docs/adr/*.md`, отдельный README лабы) был создан, затем по
запросу пользователя объединен в корневой `README.md` и `docs/details.md` -
чтобы структура проекта не показывала деление по лабораторным.

**Выполненные проверки**:

- Полное чтение исходного кода: `BusinessLogic`, `DataAccess`, `WebUI` (контроллеры, views, сессия, DI), `init.sql`, `docker-compose.yml`, `appsettings.json`, тестов.
- Синтаксис всех новых/измененных `.puml`-файлов проверен реальной компиляцией (`plantuml.jar -checkonly`, exit code 0 для всех пяти файлов).
- PNG-рендер новых BPMN и измененных диаграмм НЕ проверен визуально с читаемым результатом - в песочнице агента нет кириллического шрифта (эффект воспроизведен и на уже существующем `Use-Case.puml`, то есть проблема окружения, а не файлов). Пользователю нужно сгенерировать PNG самостоятельно обычным для проекта инструментом.
- Ссылки между новыми `.md`-файлами не проверялись автоматическим линтером (инструмента для этого в проекте нет) - проверены вручную при написании.

**Ключевые решения, принятые пользователем**:

1. Ключевые сценарии - Create Trip / Add Expense / Settlement (SC-001..003), совпадают с существующими sequence-диаграммами.
2. Auth-расхождение (Google в документации vs email в коде) фиксируется по факту: документация приведена в соответствие с кодом (email-вход), Google OAuth не выдается за реализованное поведение.
3. Заморожены как не подлежащие пересмотру: схема БД и алгоритм расчета долгов. Схема аутентификации - открыта для пересмотра (см. ADR-001).
4. TelegramBot исключен из архитектурных материалов (C4, Use Case) - вне текущего фокуса (веб).
5. NFR зафиксированы как целевые (не измеренные) ориентиры: NFR-PERF-001 (p95 < 300 мс при ~10 RPS), NFR-REL-001 (availability ≥ 99% + 0 потерь данных), NFR-SEC-001 (100% trip-scoped действий требуют членства в поездке + HttpOnly/CSRF).
6. ADR-001: раздельная авторизация - email для Web UI, token-based (JWT) для будущего REST API.
7. ADR-002: хранение изображений чеков остается в S3/MinIO (без изменений).
8. ADR-003: целевое состояние доставки - единый `docker-compose` (Postgres + MinIO + Web UI); реализация - отдельная задача.
9. Документы структурированы по смыслу (`docs/`), а не по лабораторным - отдельного README для лабы нет, все ссылки - в корневом `README.md`. (Изначально диаграммы лежали в отдельной `img/`, слита в `docs/` 2026-10-08 по запросу пользователя.)

**Отклоненные альтернативы**:

- ADR-001: полноценный Google OAuth вместо email-входа - отклонено как существенная работа вне текущего объема, требующая внешнего провайдера и секретов.
- ADR-002: BLOB в Postgres и локальная файловая система - отклонены из-за конфликта с NFR-PERF-001 и с планами на горизонтальное масштабирование.
- ADR-003: переход на Kubernetes - отклонено как избыточное для текущего масштаба проекта.
- Удаление старого `b_process.drawio` - отклонено в пользу сохранения его как обзорной схемы.

**Зафиксированные, но не исправленные пробелы** (код не менялся):

- `TripsController.Details` не проверяет членство пользователя в поездке (расхождение с целевым NFR-SEC-001).
- Атомарность операции "запись в БД + загрузка файла в S3" в `ReceiptImageService` не проверена.
- PostgreSQL и Web UI не контейнеризованы (только MinIO в `docker-compose.yml`) - целевое состояние зафиксировано в ADR-003, реализация - отдельная задача.
