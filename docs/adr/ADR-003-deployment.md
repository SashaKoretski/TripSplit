# ADR-003: Способ доставки приложения (целевое состояние)

## Статус

Принято, 2026-09-24. Реализация - отдельная задача по инфраструктуре, не
входит в текущий объем изменений.

## Контекст

Сейчас `docker-compose.yml` поднимает только MinIO (объектное хранилище) и
init-job для бакета. PostgreSQL ожидается локально запущенным
(`ConnectionStrings:Postgres` в `appsettings.json` указывает на
`localhost:5432`), Web UI запускается вручную через `dotnet run`. CI
(`.github/workflows/`) не настроен. Это затрудняет воспроизводимый запуск
"с нуля" на чужой машине.

## Рассмотренные варианты

### Вариант A - Полностью контейнеризованный docker-compose (Postgres + MinIO + Web UI)

- Плюсы: `docker compose up` поднимает весь стенд одной командой; упрощает
  как локальную разработку, так и любую будущую CI-проверку smoke-тестами.
- Минусы: нужно завести `Dockerfile` для Web UI, прокинуть переменные
  окружения вместо/поверх `appsettings.json`, продумать порядок старта
  (`depends_on` + healthcheck по аналогии с уже существующим для MinIO).
- Совместимость с текущим кодом: высокая - `Program.cs` уже читает
  конфигурацию через `IConfiguration`, переменные окружения подключаются
  автоматически (`WebApplication.CreateBuilder`).
- Стоимость изменения: умеренная, отдельная от текущих изменений.
- Риски: нужно не сломать сценарий "просто `dotnet run` без Docker" для
  локальной разработки - решается тем, что compose-стенд остается
  опциональным способом запуска, а не единственным.

### Вариант B - Оставить гибридное состояние окончательным

- Плюсы: ничего не меняется сейчас.
- Минусы: вопрос о полной контейнеризации просто откладывается без
  решения; нет зафиксированного направления, к которому готовиться.
- Совместимость: тривиальная (ничего не трогаем).
- Стоимость изменения: 0 сейчас, полная - позже.
- Риски: минимальные сейчас, откладывает неизбежное решение.

### Вариант C - Переход на Kubernetes/оркестрацию

- Плюсы: ближе к "промышленному" развертыванию.
- Минусы: явно избыточно для текущего масштаба проекта, когда еще нет даже
  единого docker-compose стенда; требует kubectl/kind/minikube без явной
  необходимости на этом этапе.
- Совместимость: низкая, большой скачок сложности.
- Стоимость изменения: высокая.
- Риски: избыточная сложность без обоснованной необходимости.

## Решение

Вариант A: целевое состояние - единый `docker-compose.yml`, поднимающий
Postgres, MinIO и Web UI. Реализация - отдельная инфраструктурная задача;
`docker-compose.yml` этим решением не редактируется.

## Последствия

- Текущее гибридное состояние инфраструктуры явно зафиксировано как
  временное, а не финальное.
- Будущая работа по контейнеризации не должна заново обсуждать, нужен ли
  единый docker-compose - это уже решено здесь.
- Deployment-диаграмма (если будет создаваться) должна отражать три
  контейнеризованных сервиса, а не два.
