# ADR-001: Схема аутентификации для Web UI и REST API

## Статус

Принято, 2026-09-24.

## Контекст

Web UI использует вход по email без пароля
(`AccountController.LoginByEmail/Register`, cookie-сессия `TripSplit.Session`).
Поле `users.google_id` исторически предполагало вход через Google OAuth,
который не реализован; сейчас в это поле пишется заглушка `"local:{email}"`.

Отдельно предстоит спроектировать и реализовать REST API. REST API обычно
должен быть stateless (не завязан на cookie-сессию конкретного браузера),
поэтому авторизация Web UI и авторизация REST API - по сути два разных
требования, которые единый email+cookie механизм не решает одинаково хорошо
для обоих случаев.

## Рассмотренные варианты

### Вариант A - Email-вход для Web UI + отдельный token-based (JWT) для REST API

- Плюсы: не требует переделки уже работающего Web UI; дает REST API чистую
  stateless-авторизацию; два механизма изолированы друг от друга, ошибка в
  одном не ломает другой.
- Минусы: два механизма аутентификации в одном проекте - больше
  поверхности для документирования и тестирования.
- Совместимость с текущим кодом: высокая - `AccountController`/`WebAppSession`
  не меняются; JWT добавляется отдельным слоем при реализации API.
- Стоимость изменения: низкая сейчас (это решение о направлении, не код),
  умеренная при реализации API (выдача и проверка токена).
- Риски: нужно явно развести, какие email/user_id используются в обеих
  системах (общий `users.id`), чтобы не расходились.

### Вариант B - Полноценный Google OAuth вместо email-входа

- Плюсы: избавляет от входа через "чужой email"; `google_id` в схеме БД
  уже под это заведен.
- Минусы: требует внешнего OAuth-провайдера, client id/secret (секреты не
  коммитятся), реального редиректа и обработки callback - существенный
  объем работы; добавляет внешнюю зависимость без явной необходимости на
  текущем этапе.
- Совместимость: `google_id` в схеме уже готов, но login-flow в
  `AccountController` нужно переписывать.
- Стоимость изменения: высокая.
- Риски: зависимость от внешнего сервиса усложняет воспроизводимую проверку.

### Вариант C - Единый механизм (email/сессия) для Web UI и REST API

- Плюсы: минимум сущностей, один механизм для всего.
- Минусы: нетипично для REST (сессия привязана к cookie конкретного
  браузера, плохо подходит для внешних интеграций и мобильных клиентов).
- Совместимость: высокая с Web UI, низкая с духом REST API.
- Стоимость изменения: низкая сейчас, но создает архитектурный долг.
- Риски: переделывать все равно придется, когда появятся внешние клиенты API.

## Решение

Вариант A: email-вход остается механизмом аутентификации Web UI без
изменений. Для REST API проектируется и реализуется отдельная token-based
авторизация (конкретный механизм - JWT или иной - решается при
проектировании API). Схема auth не заморожена - ее можно пересматривать
при необходимости.

## Последствия

- `Use-Case.puml`/`DBML.dbml` приведены в соответствие факту (email-вход).
- `users.google_id` остается в схеме как есть; вопрос, нужно ли поле для
  будущего Google OAuth или его стоит переименовать/убрать, откладывается
  до момента, когда OAuth реально понадобится - если понадобится вообще.
- Проектирование REST API обязано явно описать схему авторизации API
  (`securitySchemes`) отдельно от Web UI - прямое следствие этого решения.
