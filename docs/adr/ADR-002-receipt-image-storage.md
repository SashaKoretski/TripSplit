# ADR-002: Хранение изображений чеков

## Статус

Принято, 2026-09-24.

## Контекст

Изображения чеков (фото/скан) загружаются пользователями при добавлении
трат/чеков (FR-013, FR-015) и могут достигать нескольких мегабайт
(`ReceiptsController.MaxUploadBytes = 10 MB`). Реализовано хранение в
S3-совместимом объектном хранилище (`IFileStorageService` →
`S3FileStorageService`, в dev-окружении - MinIO через `docker-compose.yml`),
метаданные (`storage_key`, `content_type`, `file_size_bytes`,
`original_file_name`) - в таблице `receipt_images` в Postgres.

## Рассмотренные варианты

### Вариант A - S3-совместимое объектное хранилище (текущий подход)

- Плюсы: реализовано и покрыто тестами (`ReceiptImageServiceTests.cs`);
  бинарные данные не раздувают бэкапы реляционной БД; presigned URL для
  скачивания снимают нагрузку по раздаче файлов с самого приложения;
  естественно масштабируется при появлении нескольких инстансов Web UI.
- Минусы: дополнительный внешний компонент в стенде (MinIO/S3), нужно
  поднимать и настраивать отдельно от Postgres.
- Совместимость с кодом: полная - изменений не требуется.
- Стоимость изменения: 0 (сохраняем как есть).
- Риски: нет новых - компонент уже эксплуатируется.

### Вариант B - BLOB (`bytea`) в PostgreSQL

- Плюсы: один сервис хранения вместо двух, проще для локального dev-стенда.
- Минусы: раздувает объем БД и время бэкапов/восстановления; ухудшает
  производительность обычных SQL-запросов к `expenses`/`receipts` при
  больших вложениях; противоречит NFR-PERF-001 при росте числа чеков.
- Совместимость с кодом: требует переписать `IFileStorageService`,
  `ReceiptImageRepository`, миграцию схемы `receipt_images` - существенное
  изменение слоя доступа к данным.
- Стоимость изменения: высокая.
- Риски: рост размера БД, потенциальная деградация производительности со
  временем.

### Вариант C - Локальная файловая система сервера Web UI

- Плюсы: минимальная сложность прямо сейчас, не нужен S3/MinIO вовсе.
- Минусы: файлы привязаны к конкретному инстансу процесса - несовместимо с
  горизонтальным масштабированием и балансировкой нагрузки; сложнее
  бэкапить согласованно с БД.
- Совместимость с кодом: требует переписать `IFileStorageService`.
- Стоимость изменения: средняя сейчас, создает архитектурный долг при
  масштабировании.
- Риски: несовместимость с будущим горизонтальным масштабированием.

## Решение

Вариант A: сохраняем S3-совместимое хранилище (MinIO для dev,
S3-совместимый сервис для прод) без изменений. Обоснование - уже
реализовано, покрыто тестами, и единственный вариант, совместимый с
будущей балансировкой/репликацией.

## Последствия

- Код `S3FileStorageService`, `ReceiptImageService`, `ReceiptImageRepository`
  не меняется.
- В C4 Container/Component диаграммах (`img/C4/L1-L3/L1-L3.dsl`) объектное
  хранилище остается отдельным контейнером - без изменений.
- Остается открытым технический вопрос (см. `docs/requirements.md`):
  атомарность операции "запись метаданных в БД + загрузка объекта в S3" в
  `ReceiptImageService` - требует code review, не меняется этим ADR.
