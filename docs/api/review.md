# Семантическое ревью контракта (Этап 5 LAB02)

## Коды ошибок -> доменные исключения

Прямое соответствие `code` в `Error` и исключениям
`TripSplit.BusinessLogic.Models.Exceptions.*`, чтобы контракт не придумывал
ошибки, которых нет в бизнес-логике:

| HTTP | `code` | Исключение / источник |
|---|---|---|
| 400 | `validation_error` | `ArgumentException` (пустой id, не прошла базовая валидация запроса) |
| 401 | `unauthorized` | нет/невалиден Bearer-токен (новое для API, в MVC не было) |
| 403 | `forbidden` | не участник поездки (целевое поведение, см. ниже) |
| 404 | `user_not_found` | `UserNotFoundException` |
| 404 | `trip_not_found` | `TripNotFoundException` |
| 404 | `expense_not_found` | `ExpenseNotFoundException` |
| 404 | `receipt_not_found` | `ReceiptNotFoundException` |
| 404 | `receipt_image_not_found` | `ReceiptImageNotFoundException` |
| 409 | `trip_already_finished` | `TripAlreadyFinishedException` |
| 413 | `file_too_large` | транспортный лимит запроса (`RequestSizeLimit`, 10 МБ) - проверяется раньше бизнес-логики, см. Этап 7 ниже |
| 422 | `invalid_expense` | `InvalidExpenseException` (BR-02, BR-03, BR-10, BR-11) |
| 422 | `invalid_receipt_image` | `InvalidReceiptImageException` (content-type; размер - только если лимиты когда-нибудь разойдутся с 413) |

## Проверка по пунктам Этапа 5

- **GET безопасен**: все `GET` в контракте не имеют побочных эффектов,
  включая `GET /receipts/{id}/image` (редирект, не изменяет состояние).
- **PUT идемпотентен**: `PUT /expenses/{id}` - полная замена, повторный
  одинаковый вызов дает тот же результат. `PUT /receipts/{id}/image` -
  повторная загрузка того же файла дает тот же результат (новый
  `ReceiptImage.id`, но то же содержимое) - технически не строго
  идемпотентно по `id` ресурса, но идемпотентно по наблюдаемому состоянию
  (контент чека). Отмечено в описании операции.
- **DELETE - понятная повторная семантика**: везде повторный `DELETE` уже
  удаленного/не существующего ресурса -> `404`, см. раздел "Решение по
  удалению" ниже.
- **POST используется осмысленно**: создание ресурсов (`trips`, `expenses`,
  `receipts`, `users`) + два намеренных RPC-исключения (`/trips/{id}/finish`,
  `/auth/token`) - оба обоснованы в разделе "Спорные места" ниже.
- **PATCH соответствует модели**: JSON Merge Patch, отдельно описано различие
  "поле не передано" / "поле - `null`" для `receiptId`; для полей без
  осмысленного пустого состояния `null` - ошибка `400`, не тихое игнорирование.
- **200/201/202/204 не случайны**: `201` - только когда создан новый ресурс
  (с `Location`); `200` - когда операция вернула существующее/обновленное
  представление без создания нового ресурса; `204` - `DELETE` без тела.
  Нет `202` - в системе нет асинхронных операций.
- **400/401/403/404/409/422 различаются осмысленно**: `400` - запрос
  синтаксически/структурно некорректен; `401` - нет личности; `403` - есть
  личность, но нет прав; `404` - ресурса нет; `409` - ресурс есть, но в
  состоянии, конфликтующем с операцией (`Trip.status = finished`); `422` -
  запрос синтаксически корректен, но нарушает бизнес-правило.
- **Location используется**: везде, где `201 Created` (новая поездка, трата,
  чек, пользователь).
- **Обязательные поля обязательны**: `required` в схемах запросов совпадает
  с проверками конструкторов `Trip`/`Expense`/`Receipt`/`User` (ArgumentException
  при отсутствии).
- **readOnly/writeOnly корректны**: `id`, `createdAt`, `updatedAt`,
  `effectiveAmount`, `Trip.status` (кроме перехода через `/finish`) -
  `readOnly`. `writeOnly` не использован - в контракте нет полей вроде
  пароля, которые нужно принимать, но нельзя возвращать.
- **enum отражают бизнес-правила**: `ExpenseType` - те же 5 значений, что и
  CHECK-constraint `expenses.type` в `init.sql`; `Trip.status` -
  `active`/`finished`, как в БД.
- **Нет утечки внутренней DB-модели**: наружу не отданы `google_id`
  (технический артефакт, в документации WebLab#1 уже помечен как расхождение
  с фактическим email-входом), `deleted_at`, `storage_key` S3-объекта.

## Спорные места, вынесенные до финализации

Это механические, но не всегда однозначные решения, принятые при черновике.
**Все пять подтверждены пользователем как есть** (2026-10-07), пересмотр не
требуется.

1. **`POST /users` с уже занятым email -> `200`, не `409`.** Бизнес-правило
   BR-08 (уже принято в WebLab#1, не пересматривается) говорит: повторная
   регистрация с занятым email входит в существующий аккаунт. Для чистого
   REST дублирующий `POST` на создание обычно - `409 Conflict`. Выбрано
   `200 OK` с существующим `User`, потому что это точнее отражает факт "ресурс
   не был создан этим вызовом, но запрос не является ошибкой" - именно так
   ведет себя `UserService.RegisterAsync`. Альтернатива `409` потребовала бы
   трактовать штатное поведение как ошибку клиента, что не соответствует
   смыслу BR-08.

2. **`POST /trips/{id}/participants` для уже существующего участника -> `200`,
   не `409` и не `201`.** `TripService.AddParticipantAsync` тихо не делает
   ничего, если пользователь уже участник (не бросает исключение). Контракт
   повторяет это как идемпотентный `200` с уже существующей записью, а не
   выдает ошибку, которой в бизнес-логике нет.

3. **`PUT /receipts/{id}/image` всегда возвращает `200`, не `201` при первой
   загрузке.** `ReceiptImageService.UploadAsync` всегда сначала удаляет
   предыдущее изображение (если было), затем создает новое - для сервиса это
   единообразная операция "текущее изображение чека", без явного различения
   "впервые" / "замена". Разбирать это различие в контракте означало бы
   добавлять знание, которого нет в сервисе. Если для защиты важно строго
   возвращать `201` при первой загрузке - это небольшое, но реальное
   изменение сервиса (добавить проверку "было ли изображение раньше"), не
   меняющее бизнес-правила, можно сделать в WebLab#3.

4. **`DELETE /receipts/{id}` не проверяет статус поездки (не дает `409` для
   завершенной поездки), в отличие от `POST /trips/{id}/receipts`.** Это
   прямое следствие текущего кода - `ReceiptService.DeleteAsync` не содержит
   проверки `TripStatus.Finished`, хотя `CreateAsync` ее содержит. Налицо
   асимметрия в существующей бизнес-логике (можно удалить чек завершенной
   поездки, но не создать новый). Контракт описывает фактическое поведение,
   не исправляя бизнес-правило молча (прямой запрет LAB02: "не меняй бизнес-
   правила, чтобы было удобнее REST"). Если асимметрия нежелательна -
   решение о том, добавлять ли проверку, принадлежит WebLab#3.

5. **`POST /auth/token` с незарегистрированным email -> `404 user_not_found`,
   не `401`.** Типичная практика для публичных auth-эндпоинтов - не
   подтверждать/отрицать существование аккаунта через статус (anti-
   enumeration), обычно `401` в обоих случаях. Выбран `404`, потому что:
   (а) в системе нет паролей и секретов, которые имело бы смысл защищать от
   enumeration - email и так раскрывается при приглашении участника
   (`addTripParticipant` тоже возвращает `404`, если email не зарегистрирован);
   (б) это прямое повторение текущего UX Web UI, который явно показывает
   "аккаунт не найден, зарегистрируйтесь" (`AccountController.LoginByEmail`).
   Если для защиты нужна anti-enumeration семантика - это значимое изменение
   модели безопасности, выходящее за рамки согласованного ADR-001, и его
   стоит обсуждать отдельно, а не менять тихо.

## Управляемое изменение (Этап 7 LAB02, подтверждено пользователем 2026-10-07)

**Найденная проблема**: `PUT /receipts/{id}/image` описывал загрузку файла
без конкретики, хотя в коде есть точные цифры - `ReceiptsController.
MaxUploadBytes = 10 МБ` (`[RequestSizeLimit]`, транспортный уровень
ASP.NET) и `ReceiptImageOptions.MaxFileSizeBytes = 10 МБ` +
`AllowedContentTypes = {image/jpeg, image/png, image/webp, application/pdf}`
(бизнес-уровень, `ReceiptImageService`). Это два независимо заданных лимита,
сейчас совпадающих по значению, но не связанных в коде - контракт их не
отражал вообще.

**Изменение**:

- `requestBody.content.multipart/form-data.schema.properties.file` - добавлен
  `maxLength: 10485760` (10 МБ в байтах) и описание лимита.
- Добавлен `encoding.file.contentType` с явным списком 4 допустимых MIME-типов
  (стандартный способ ограничить content-type файла в multipart по спеке
  OpenAPI, не через `enum` на бинарном поле).
- Добавлен новый ответ `413 Payload Too Large` (`code: file_too_large`) -
  отдельно от `422 invalid_receipt_image`, чтобы явно развести "запрос
  отклонен транспортным лимitом до бизнес-логики" и "запрос дошел до
  `ReceiptImageService`, но не прошел его проверку" (content-type, либо
  размер - если лимиты когда-нибудь разойдутся).
- `code` enum в `components.schemas.Error` - добавлено значение
  `file_too_large`.

**Повторные проверки после изменения**:

- `npm run lint` -> `0` ошибок, `0` предупреждений (как и до изменения).
- `prism mock` - все 24 маршрута, включая `PUT /receipts/{id}/image`,
  резолвятся без ошибок `$ref`.
- `docs/api/scenario-mapping.md` обновлена: шаг "Загрузить фото к новому
  чеку" в SC-002 теперь ссылается на `413` отдельно от `422`.

## Решение по удалению (DELETE)

- **Trip, Expense** - логическое удаление (`deleted_at` в схеме БД заложен).
  Повторный `DELETE` -> `404` (ресурс для API "не существует").
  Уточнение: сейчас в контракте для `Trip` нет собственного `DELETE` -
  поездки не удаляются ни в одном сценарии WebLab#1 (только завершаются), и
  `ITripService` не содержит метода удаления. `DELETE /trips/{id}` не
  добавлен в контракт - это не недосмотр, а отсутствие потребности и
  отсутствие бизнес-логики для этого.
- **Receipt, ReceiptImage** - физическое удаление (нет `deleted_at`,
  `ON DELETE CASCADE`). Повторный `DELETE` -> `404` (строки действительно
  больше нет).
- В обоих случаях наблюдаемое поведение для клиента API одинаковое
  (`204` -> `404` при повторе) - разница soft/hard delete не протекает в
  контракт, она касается только того, что происходит на уровне БД.

## Не покрыто этим контрактом (сознательно, не относится к WebLab#2)

- `PATCH`/`PUT` для `User`, `Trip` (переименование, смена валюты) - в
  бизнес-логике нет соответствующих методов (`IUserService`, `ITripService`),
  добавлять их значило бы писать новую бизнес-логику в лабе про контракт.
- Refresh-токены, revocation/logout API - см. ADR по авторизации (раздел
  "Авторизация" в `docs/api/README.md`); явно отложено, не забыто.
- Фильтрация/сортировка коллекций - не нужны ни одному сценарию WebLab#1.

### Результат lint

```text
> redocly lint

Woohoo! Your API description is valid.
```

`0` ошибок, `0` предупреждений. По дороге линтер реально нашел и заставил
исправить:

- 3 ошибки `nullable: true` - недопустимо в OpenAPI 3.1 (JSON Schema
  2020-12), заменено на `type: [string, "null"]` (`Expense.receiptId`,
  `CreateExpenseRequest.receiptId`, `PatchExpenseRequest.receiptId`);
- 9 предупреждений `no-invalid-media-type-examples` - примеры содержали
  нереалистичные id (`"u1"`, `"r1"`, `"b7e5..."`) вместо валидных UUID,
  исправлено на настоящие UUID-подобные значения;
- `no-illogical-composition-keywords` - `ReplaceExpenseRequest` был `allOf`
  с единственной схемой; убран, `PUT /expenses/{id}` ссылается на
  `CreateExpenseRequest` напрямую.

Два правила отключены осознанно, с обоснованием в `src/openapi/redocly.yaml`
(`info-license` - в проекте нет лицензии; `operation-2xx-response` - у
`GET /receipts/{id}/image` по дизайну единственный успешный ответ - `302`).

### Результат mock-проверки (Prism, `src/openapi/package.json` -> `npm run mock`)

Prism при старте вывел все 24 маршрута контракта без ошибок резолва `$ref` -
независимое от Redocly подтверждение, что схема целиком валидна.

Прогнан многошаговый сценарий SC-002/SC-003 (`curl` к `http://127.0.0.1:4010`):

| Шаг | Запрос | Ответ |
|---|---|---|
| Создать поездку | `POST /trips` | `201` |
| Создать чек | `POST /trips/{id}/receipts` | `201` |
| Создать трату | `POST /trips/{id}/expenses` | `201` |
| Получить трату | `GET /expenses/{id}` | `200` |
| Привязать к чеку | `PATCH /expenses/{id} {"receiptId": "..."}` | `200` |
| Отвязать от чека | `PATCH /expenses/{id} {"receiptId": null}` | `200` |
| Получить расчет | `GET /trips/{id}/settlement` | `200`, тело совпало с заданным в контракте примером |
| Удалить трату | `DELETE /expenses/{id}` | `204` |
| Завершить поездку | `POST /trips/{id}/finish` | `200` |
| Негативный кейс: `POST /trips` без обязательных полей | - | `400`, тело ответа совпало со схемой `Error` (`code: validation_error`) |

Все статусы совпали с объявленными в контракте. **Важная оговорка** (прямо
по LAB02: "не считай mock server проверкой реальной бизнес-логики"): Prism в
статическом режиме не хранит состояние между вызовами - значения в телах
ответов (кроме явно заданных `examples`) генерируются по схеме, а не
отражают реальные данные из предыдущих шагов. Проверено только то, что
запросы/ответы соответствуют объявленным схемам и статусам, не то, что
бизнес-правила (BR-02..11) реально исполняются - это будет проверяться в
WebLab#3 реальными unit/integration-тестами backend.
