## Актуальность

Количество путешествующей и выезжающей на природу молодежи с каждым годом
[растет](https://iz.ru/1910554/2025-06-27/rossianam-rasskazali-o-tratah-i-otdyhe-molodezi),
однако бюджет на такие поездки, например, у неработающего студента, может быть
не таким большим как бы хотелось. Поэтому важно фиксировать все траты, чтобы
по итогу не оставалось должников. Также у населения
[повышается](https://www.vedomosti.ru/press_releases/2025/07/01/finansovaya-gramotnost-v-rossii-pervie-rezultati-i-novie-vizovi-natsionalnoi-strategii)
финансовая грамотность, поэтому людям пригодится приложение, по которому
можно следить, на что в определенной поездке были потрачены деньги.

## Тип приложения

TripSplit реализуется как многостраничное веб-приложение (Web MPA),
работающее в браузере пользователя. Приложение состоит из нескольких
логически обособленных страниц - в частности, страницы создания и ведения
текущей поездки с калькулятором расходов и страницы истории завершенных
поездок.

## Открытые технические вопросы по NFR

- Не проверена атомарность операции "запись в БД + загрузка файла в S3" в `ReceiptImageService" (риск для надежности при частичном сбое).
- `TripsController.Details` не проверяет членство пользователя в поездке - расхождение с целевым требованием безопасности (проверяет только факт входа в систему, не участие в конкретной поездке).

## Полные пользовательские сценарии

### SC-001 - Создание поездки и приглашение участников

- **Актор**: Пользователь (аутентифицирован)
- **Предусловия**: пользователь вошел в систему; поездок может не быть
- **Основной поток**: открывает список поездок → заполняет форму создания (название, валюта) → `Trip` создается со статусом `Active`, организатор становится первым участником → открывает детали поездки → вводит email приглашаемого → пользователь ищется по email и добавляется в участники.
- **Альтернативные ветки**: A1 - пользователь сам присоединяется по id поездки; A2 - приглашение нескольких участников подряд.
- **Ошибки**: E1 - пустое название/невалидная валюта - форма не отправляется; E2 - приглашаемый email не зарегистрирован - участник не добавлен, понятная ошибка; E3 - поездка уже завершена - ошибка, без изменений.
- **Постусловия**: новая строка `trips` (Active), минимум одна строка `trip_participants`.
- **Затронутые сущности**: `User`, `Trip`.
- **Экраны**: список поездок (форма создания/присоединения), детали поездки (форма приглашения, список участников).
- **Критерии приемки**: после создания поездка видна у организатора, он единственный участник; невалидная валюта не создает поездку; приглашение незарегистрированного email не меняет участников; успешный инвайт виден в деталях поездки.

### SC-002 - Добавление траты с чеком

- **Актор**: Участник поездки
- **Предусловия**: поездка выбрана активной; статус `Active`
- **Основной поток**: открывает форму добавления траты → заполняет название, тип, сумму, скидку, плательщика, потребителей, опционально чек (существующий/новый с фото) → трата сохраняется, при необходимости создаются чек и изображение → трата видна в списке.
- **Альтернативные ветки**: A1 - привязка к существующему чеку; A2 - без чека; A3 - чек создается отдельно и траты привязываются к нему позже.
- **Ошибки**: E1 - поездка завершена (проверяется и в контроллере, и в сервисе) - трата не создается; E2 - не выбран потребитель; E3 - скидка больше суммы; E4 - сумма ≤ 0; E5 - файл чека не проходит валидацию; E6 - плательщик/потребитель не участник поездки, либо чек из другой поездки (в обычном UI-потоке недостижимо, актуально при прямом обращении к API).
- **Постусловия**: новая `expense` (+ строки `expense_consumers`), опционально новые `receipt`/`receipt_image`.
- **Затронутые сущности**: `Expense`, `Receipt`, `ReceiptImage`, `User`.
- **Экраны**: форма добавления траты, список трат, создание чека, привязка трат к чеку.
- **Критерии приемки**: трата с N потребителями создает N строк распределения и делится поровну; трата в завершенной поездке не создается; скидка больше суммы отклоняется; загрузка чека при добавлении траты создает связанные записи.

### SC-003 - Завершение поездки и расчет долгов

- **Актор**: Участник поездки
- **Предусловия**: поездка активна; траты не обязательны
- **Основной поток**: нажимает "Завершить поездку" → статус меняется на `Finished` → система собирает все траты, считает баланс каждого участника и минимальный набор переводов (жадный алгоритм) → показывается итог.
- **Альтернативные ветки**: A1 - предварительный просмотр расчета до завершения поездки; A2 - поездка без трат - нулевой итог, без ошибки.
- **Ошибки**: E1 - повторное завершение уже завершенной поездки - статус не меняется, ошибка; E2 - просмотр расчета без выбранной поездки - редирект с просьбой выбрать поездку.
- **Постусловия**: `Trip.Status = Finished`; сам расчет не хранится в БД, пересчитывается каждый раз.
- **Затронутые сущности**: `Trip`, `Expense`, производные `Transfer`/`TripStatistics` (не персистятся).
- **Экраны**: детали поездки (кнопка завершения), итог/расчет долгов.
- **Критерии приемки**: после завершения статус `Finished` и новые траты запрещены; сумма переводов покрывает каждый отрицательный баланс полностью; число переводов не больше (число участников с ненулевым балансом − 1) - свойство жадного алгоритма, не гарантия глобального минимума; повторное завершение не меняет данные.

## Полные архитектурные решения (ADR)

### ADR-001: схема аутентификации

**Контекст**: Web UI использует email-вход без пароля; поле `google_id`
исторически предполагало Google OAuth, который не реализован. Предстоит
REST API, обычно stateless, для которого email+cookie не подходит напрямую.

**Альтернативы**:
- A. Email для Web UI + отдельный token-based (JWT) для REST API. Плюсы: не
  трогает рабочий Web UI, дает API чистую stateless-авторизацию, механизмы
  изолированы. Минусы: два механизма вместо одного.
- B. Полноценный Google OAuth вместо email-входа. Плюсы: соответствует
  `google_id` в схеме. Минусы: внешний провайдер, секреты, существенный
  объем работы без явной необходимости сейчас.
- C. Единый механизм email/сессия для UI и API. Плюсы: минимум сущностей.
  Минусы: нетипично для REST, придется переделывать при появлении внешних
  клиентов API.

**Решение**: A. Email-вход остается механизмом Web UI; для REST API -
отдельная token-based авторизация. Схема auth не заморожена, можно
пересматривать.

**Причина**: не требует переделки работающего UI, дает API правильную для
REST модель авторизации, оба механизма развиваются независимо.

### ADR-002: хранение изображений чеков

**Контекст**: изображения чеков могут достигать нескольких мегабайт.
Реализовано хранение в S3-совместимом хранилище (MinIO для dev), метаданные
- в Postgres.

**Альтернативы**:
- A. S3-совместимое хранилище (текущее). Плюсы: реализовано и покрыто
  тестами, не раздувает бэкапы БД, presigned URL снимают нагрузку с
  приложения, масштабируется при нескольких инстансах. Минусы: отдельный
  компонент инфраструктуры.
- B. BLOB (`bytea`) в PostgreSQL. Плюсы: один сервис вместо двух. Минусы:
  раздувает БД и бэкапы, ухудшает производительность обычных запросов.
- C. Локальная файловая система сервера. Плюсы: минимальная сложность
  сейчас. Минусы: несовместимо с горизонтальным масштабированием.

**Решение**: A, без изменений.

**Причина**: уже реализовано и протестировано, единственный вариант,
совместимый с будущим масштабированием.

### ADR-003: способ доставки приложения

**Контекст**: `docker-compose.yml` сейчас поднимает только MinIO; Postgres и
Web UI запускаются вручную. Это затрудняет воспроизводимый запуск с нуля.

**Альтернативы**:
- A. Полностью контейнеризованный docker-compose (Postgres + MinIO + Web
  UI). Плюсы: единая команда запуска всего стенда. Минусы: нужен `Dockerfile`
  для Web UI и настройка порядка старта.
- B. Оставить гибридное состояние как есть. Плюсы: ничего не меняется.
  Минусы: вопрос просто откладывается без решения.
- C. Переход на Kubernetes. Плюсы: ближе к промышленному развертыванию.
  Минусы: явно избыточно для текущего масштаба проекта.

**Решение**: A, как целевое состояние; сама реализация - отдельная задача,
`docker-compose.yml` этим решением не редактируется.

**Причина**: естественный следующий шаг к воспроизводимому стенду, не
требует серьезных изменений в существующем коде.

## Сборка и запуск (подробно)

Из папки `src`:

```powershell
dotnet build -c Release           # сборка всех компонентов
dotnet test                       # тесты

dotnet publish TripSplit.ConsoleUI -c Release -o publish   # публикация всех .dll в src\publish\

# Web UI
dotnet run --project TripSplit.WebUI
# затем открыть URL http://localhost:7717
```

Запуск напрямую из ОС - двойной клик по `src\publish\TripSplit.ConsoleUI.exe`
(или `.\publish\TripSplit.ConsoleUI.exe` в PowerShell).
