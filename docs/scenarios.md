# TripSplit - пользовательские сценарии

Три ключевых сценария системы. Совпадают с sequence-диаграммами
(`img/UML/CreateTrip_UML.puml`, `AddExpense_UML.puml`, `Settlement_UML.puml`)
и с BPMN-процессами (`img/Business-process/bpmn-create-trip.puml`,
`bpmn-add-expense.puml`, `bpmn-settlement.puml`).

## SC-001 - Создание поездки и приглашение участников

- **Актор**: Пользователь (аутентифицирован, FR-001/FR-002)
- **Предусловия**: пользователь вошел в систему; у него может не быть ни одной поездки
- **Основной поток**:
  1. Открывает `Trips/Index`, видит список своих поездок и формы Create/Join.
  2. Заполняет форму создания: название, валюта (ISO 4217).
  3. `TripsController.Create` → `TripService.CreateAsync`: создается `Trip` со статусом `Active`, организатор добавляется первым участником, поездка становится активной в сессии.
  4. Открывается `Trips/Details`; на этой странице вводит email того, кого хочет пригласить.
  5. `TripsController.Invite` ищет пользователя по email (через `google_id = "local:{email}"`); если найден - добавляет в `trip_participants`.
- **Альтернативные ветки**:
  - A1: вместо приглашения другой пользователь сам присоединяется по известному ему id поездки (`TripsController.Join`, FR-005).
  - A2: приглашающий добавляет нескольких участников последовательно, повторяя шаг 5.
- **Ошибки**:
  - E1: название пустое или валюта не из 3 букв → `ModelState` невалиден, форма `Trips/Index` перерисовывается с ошибками, поездка не создается.
  - E2: приглашаемый email не зарегистрирован в системе → `TempData["Error"] = "Пользователь с таким email не зарегистрирован..."`, участник не добавлен.
  - E3: попытка пригласить/присоединиться к уже завершенной поездке → `TripAlreadyFinishedException` → `DomainExceptionFilter` → редирект с сообщением об ошибке.
- **Постусловия**: в БД новая строка `trips` (Active) и минимум одна строка `trip_participants`; для успешного инвайта - вторая строка `trip_participants`.
- **Связанные требования**: FR-004, FR-005, FR-006, FR-007, FR-008, BR-01, BR-09.
- **Затронутые сущности**: `User`, `Trip`.
- **Экран/UI**: `Views/Trips/Index.cshtml` (формы Create/Join), `Views/Trips/Details.cshtml` (форма Invite, список участников).
- **Критерии приемки**:
  - AC1: после успешного Create поездка видна в `Trips/Index` у организатора, и он единственный участник.
  - AC2: валюта не из 3 букв не создает `Trip` (см. `Trip` constructor, BR-01).
  - AC3: приглашение незарегистрированного email не меняет `trip_participants` и показывает понятную ошибку (E2).
  - AC4: после успешного инвайта приглашенный виден в `Trip.ParticipantIds` на `Trips/Details`.

## SC-002 - Добавление траты с чеком

- **Актор**: Участник (пользователь, входящий в `Trip.ParticipantIds` выбранной поездки)
- **Предусловия**: поездка выбрана активной в сессии (`AppSession.CurrentTripId`); `Trip.Status == Active`
- **Основной поток**:
  1. Открывает `Expenses/Create` (GET); подтягиваются участники поездки и уже существующие чеки без привязанных трат.
  2. Заполняет форму: название, тип, сумма, скидка, плательщик, список потребителей (по умолчанию - все участники); опционально выбирает существующий чек или вводит данные нового чека + прикладывает файл.
  3. `ExpensesController.Create` (POST) валидирует (≥1 потребитель, скидка ≤ суммы) и вызывает `ExpenseService.AddAsync`.
  4. Если приложен файл нового чека: сначала `ReceiptService.CreateAsync`, затем `ReceiptImageService.UploadAsync` (загрузка в S3/MinIO + метаданные в БД), затем трата создается с этим `ReceiptId`.
  5. Редирект на `Expenses/Index` - новая трата видна в списке, итоговая сумма поездки пересчитана.
- **Альтернативные ветки**:
  - A1: трата привязывается к уже существующему чеку (`receiptId` передан явно) вместо создания нового.
  - A2: трата создается вовсе без чека (`ReceiptId = null`).
  - A3: чек создается заранее (`Receipts/Create`), а траты привязываются к нему позже через `AttachExpenses` (FR-014).
- **Ошибки**:
  - E1: поездка уже завершена → на уровне UI GET `Expenses/Create` сразу редиректит на `Index` с `TempData["Error"]`, форма не открывается; на уровне домена `ExpenseService.AddAsync` независимо проверяет `Trip.Status` и бросает `TripAlreadyFinishedException` (защита в глубину, а не только в контроллере).
  - E2: не выбран ни один потребитель → `ModelState` ошибка "Выберите хотя бы одного получателя".
  - E3: скидка больше суммы → `ModelState` ошибка, форма перерисовывается с введенными данными.
  - E4: сумма ≤ 0 или скидка < 0 → `InvalidExpenseException` из домена (конструктор `Expense`) → `DomainExceptionFilter` → редирект с ошибкой.
  - E5: файл чека не проходит валидацию (тип/размер) → `InvalidReceiptImageException` → `DomainExceptionFilter`.
  - E6: плательщик или один из потребителей не входит в участников поездки (BR-10), либо выбранный чек принадлежит другой поездке (BR-11) → `InvalidExpenseException`/`InvalidExpenseException` из `ExpenseService` → `DomainExceptionFilter`. В обычном UI-потоке недостижимо (форма предлагает только участников и чеки текущей поездки), но обязательно к покрытию в WebLab#2/3, где вход - JSON, а не форма.
- **Постусловия**: новая строка `expenses` (+ N строк `expense_consumers`); опционально новые строки `receipts`/`receipt_images`.
- **Связанные требования**: FR-009, FR-012, FR-013, FR-014, FR-015, BR-02, BR-03, BR-04, BR-05, BR-07.
- **Затронутые сущности**: `Expense`, `Receipt`, `ReceiptImage`, `User` (плательщик и потребители).
- **Экран/UI**: `Views/Expenses/Create.cshtml`, `Views/Expenses/Index.cshtml`, `Views/Receipts/Create.cshtml`, `Views/Receipts/AttachExpenses.cshtml`.
- **Критерии приемки**:
  - AC1: успешная трата с N потребителями создает ровно N строк `expense_consumers`, и `EffectiveAmount` делится поровну (проверяется через SC-003).
  - AC2: попытка добавить трату в завершенную поездку не создает записи в БД (E1 срабатывает до сохранения).
  - AC3: скидка больше суммы отклоняется без создания `Expense` (E3/E4).
  - AC4: одновременная загрузка чека при добавлении траты создает связанные `Receipt` + `ReceiptImage`, и `Expense.ReceiptId` указывает на них.

## SC-003 - Завершение поездки и расчет долгов

- **Актор**: Участник
- **Предусловия**: поездка активна (`Status == Active`); наличие трат не обязательно (пустая поездка - валидный кейс)
- **Основной поток**:
  1. На `Trips/Details` нажимает "Завершить поездку" (`TripsController.Finish`).
  2. `TripService.FinishAsync`: `Trip.Status = Finished`; редирект на `Settlement/Index`.
  3. `DebtSettlementService.CalculateSettlementAsync`: собирает все траты поездки, считает `TotalSpent`, `PerUserSpent` и баланс каждого участника (оплачено − доля потребленного).
  4. `GreedyDebtMinimizationStrategy.Minimize` строит минимальный набор переводов, закрывающий все балансы.
  5. `Settlement/Index` показывает итоговую сумму, траты по участникам и список переводов "кто кому сколько должен".
- **Альтернативные ветки**:
  - A1: `Settlement/Index` можно открыть и до завершения поездки - промежуточный (предварительный) расчет по текущим тратам, без изменения `Trip.Status`.
  - A2: в поездке нет ни одной траты → `TotalSpent = 0`, пустой список переводов (ранний return в `DebtSettlementService`, без ошибки).
- **Ошибки**:
  - E1: повторная попытка завершить уже завершенную поездку → `TripAlreadyFinishedException` → `DomainExceptionFilter` → редирект с ошибкой, статус не меняется.
  - E2: просмотр `Settlement` без выбранной активной поездки → `TripAwareController.ResolveCurrentTripAsync` редиректит на `Trips/Index` с "Сначала выберите поездку".
- **Постусловия**: при успешном `Finish` - `Trip.Status = Finished` в БД; сам расчет переводов (`TripStatistics`, `Transfer`) не персистится, вычисляется каждый раз заново по данным `expenses`.
- **Связанные требования**: FR-016, FR-017, BR-05, BR-06.
- **Затронутые сущности**: `Trip`, `Expense`, производные `TripStatistics`/`Transfer` (не хранятся в БД).
- **Экран/UI**: `Views/Trips/Details.cshtml` (кнопка Finish), `Views/Settlement/Index.cshtml`.
- **Критерии приемки**:
  - AC1: после `Finish` статус `Finished`, и попытки добавить трату/чек блокируются (пересекается с SC-002 E1).
  - AC2: сумма переводов, входящих в план каждого должника, равна его отрицательному балансу (баланс каждого участника закрывается полностью).
  - AC3: число переводов не превышает `(число участников с ненулевым балансом − 1)` - свойство жадного алгоритма; это не гарантия глобального минимума (алгоритм жадный, не точный ILP-solver) - фиксируется как известное ограничение, а не баг.
  - AC4: повторный `Finish` (E1) не меняет `Trip.Status` и не создает побочных эффектов.
